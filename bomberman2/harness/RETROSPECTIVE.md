# 复盘：Bomberman II 反汇编流程，以及下一个游戏怎么做

## 1. 结果

- 一份源码，美日两版逐字节重建；重定位测试 48/48。
- 静态检查：指针嫌疑和「代码当数据」都为 0。
- 例程全部命名，RAM 命名约 400 个。
- IF 块里的行数从 1965 降到 1356，剩下的都是真实差异。
- grok 消耗：新输入约 4.3M token，缓存输入 132.5M，输出 1.06M，工具调用 2053 次（被拒 37 次）。

## 2. 做对了、下次保留的

1. **把正确性当硬约束**。字节一致和重定位测试（PPU/APU 写入流逐条比较）都是机器判定。agent 犯的错，最后都是被这两项抓住的。
2. **源码由生成器产出，人只改数据库**。agent 只能通过 `db.py` 改数据库，生成的 asm 不会被改坏。每次修正都能重新生成、重新验证。
3. **taint 追踪找指针**。运行时自动找出拆分表、立即数指针、`ADC #base` 这类写法，比人工找快得多，也更准。
4. **分片加 worktree 并行，配合最小权限**。dontAsk 白名单加沙箱，grok 越界的尝试（写脚本、`python -c`、改别的分片）全部被挡住。
5. **验收者跑全量检查**。快速检查漏掉的两处真错误（坐标被当成指针、日版指针缺失），都是 `check.sh --full` 抓到的。

## 3. 浪费在哪里（按代价从高到低）

| 问题 | 代价 | 根因 | 下次 |
|---|---|---|---|
| 日版覆盖率不全，很晚才发现 | 日版指针大量靠后补，合并迭代很多轮 | 关卡场景强制写的是美版 RAM 地址；日版 RAM 布局不同，日版一直停在第 1 区 | 每个区域的场景都要截图确认到达；RAM 地址按区域配置 |
| 美日合并反复重做 | 我这边的大量 token | 先按 token 对齐，后改字节对齐；传播规则先松后紧 | 一开始就用：字节对齐、RAM 符号、指针配对、跨区域指针、名字统一（本次最终方案） |
| harness 启动摩擦 | 几轮 grok 白跑（约 15M 缓存 token），半天调试 | UTF-8 变量展开、dontAsk 下复合命令和 `$` 被拒、运行中改 run.sh、pgrep 自匹配、zsh 不分词 | 先跑一个 5 分钟的 smoke 任务验证权限；RULES 一开始就写全；run.sh 冻结后再并行 |
| grok 长会话 | T01 一个任务就用了 44.6M 缓存 token | 一个任务 70 多个例程、500 多次调用，而且反复用 read_file 读整个 bank | 每个任务不超过 40 个例程；`q.py pack` 一次给足上下文；禁止读整个 bank 文件 |
| 自写模拟器调试 | NMI 时序、PPU、DPCM、越界读、帧边界比较 | 从零写 | 这套 emu 已经可用，下次直接复用，抽象出 mapper 层 |
| 任务顺序 | T09 起的日版名字后来被名字统一机制取代；T10 本该由工具完成 | 结构性工作（指针、代码声明、区域对齐）和命名混在 agent 阶段 | 结构性工作全部在命名之前由工具和 Claude 完成，agent 只做命名和注释 |

## 4. 下一个游戏的推荐流程

**阶段 0：资料（半小时）**
- mapper、PRG/CHR 布局。
- Data Crystal 或 TCRF 的 RAM map；已有的反汇编。
- 是否有多个区域版本。

**阶段 1：结构（Claude 和工具，不用 agent）。** 每一步都有机器判定的完成标准。
1. 把 `tools/` 抽成通用库，游戏相关的放进配置：mapper、跨 bank 调用的识别模式、关卡和命数的 RAM 地址（每个区域一份）、场景脚本。
2. 覆盖场景：每个场景截图确认到达目标画面（标题、各模式、各关、结局）。
3. 静态追踪、taint、生成源码。字节一致。
4. 重定位测试：shift 1 和 256，全场景。
5. 多区域：字节对齐、RAM 符号、指针配对、跨区域指针、名字统一。
6. 静态检查清零：`suspects`、`codeguess`、跨区域一致性检查（见 `merge.py` 的 `cross_pointers`）。
7. 定稿结构，提交。

**阶段 2：harness smoke test（5 分钟）**
- 用一个只命名 3 个例程的小任务，验证权限、日志、结果收集、check 全链路。

**阶段 3：命名（agent 并行）**
1. 内核任务先跑，建立 glossary。
2. 再按模块并行，每个任务不超过 40 个例程。RAM 只写提议。
3. RAM 统一命名。
4. 最后做区域差异注释。这时合并已经稳定，不会再被取代。

**阶段 4：验收**
- 每批 agent 工作之后：`check.sh --full`（并行，约 20 分钟）。
- 疑问清单逐条处理，抽查名字和注释。

## 5. 省 token 的具体措施

**agent 侧**
- 加 `q.py pack ROUTINE`：一次输出代码、调用者、被调用者、RAM 读写和相关笔记，替代多次 read_file 和 grep。
- RULES 禁止读整个 `bank*.asm`，读源码只走 `q.py`。
- `--max-turns` 设在 150 左右，任务拆小。会话越短，每轮重发的上下文越少，这是缓存 token 的大头。
- 机械性任务（例如给 notptr 写理由）用较低的 reasoning effort。

**Claude 侧**
- 等待都交给后台任务通知，不用轮询；大输出（全量 IF 块、反汇编）先汇总再看。
- 结构问题用一个分类脚本一次统计（本次的 IF 块分类器），不逐个打开文件看。

## 6. 现成工具的取舍

| 工具 | 本项目的结论 |
|---|---|
| 自写 `emu.py` | 保留。taint 和重定位比较需要逐指令钩子，而且时序近似反而让比较更稳 |
| MesenCE | 适合人工调试（调试器、CDL、Lua）。可作为准确模拟器的第二意见，或用来人工确认画面含义（敌人种类、道具） |
| cynes | 最终验收时，用准确时序比较原版和重建版的画面。重定位后的版本时序会变，不适合逐帧比 |
| crudNES、retrodisasm、da65 | 可以拿来对照初始的代码和数据划分。本项目的生成器已经覆盖跨 bank 调用、指针、多区域，不必替换 |
